# Decision Log

A list of non-obvious engineering and design decisions made while building the Uber Support Copilot, with the rationale behind each choice.

* **1. Selecting `@Uber_Support` over retail or airline brands:** Ride-hailing features rapid turnarounds with high-consequence edge cases (physical passenger safety, driver conduct, card/wallet overcharges, stranded passengers). This made the trade-off between autonomous reply drafting and human escalation realistic and testable.
* **2. Down-weighting domain-level stopwords (`driver`, `ride`, `trip`, `uber`, `car`):** In the Uber support dataset, over 90% of customer messages contain words like "driver" or "ride", regardless of whether the issue is an assault, a lost item, or an overcharge. Treating these terms equally caused naive classifiers to pull payment and safety complaints into `trip_or_pickup`. We weighted specific problem signals (`charge double`, `paytm`, `unsafe`, `lost my`) significantly higher than generic nouns.
* **3. Enforcing a "sticky" escalation policy:** LLMs are prone to overconfidence and fluent hallucinations. If deterministic safety checks detect a financial discrepancy, property damage, or driver misconduct incident, the decision is permanently locked to `ESCALATE` with a red badge, preventing the generative layer from overriding it to auto-handle.
* **4. Never auto-authorizing refunds or financial compensation:** Historical agent responses frequently promised "we've refunded your fare." Autonomous agents must never promise monetary compensation without transactional backend verification. The copilot drafts empathy and requests details (e.g., Paytm transaction ID, trip date) while routing the ticket to an agent queue.
* **5. Separating routing logic from reply drafting:** Both components share the same retrieved evidence cases, but the decision of whether to auto-handle or escalate runs on deterministic safety invariants rather than relying on generative LLM token probabilities.
* **6. Multi-turn conversation parsing vs. raw text concatenation:** Raw TWCS conversations frequently contain Twitter setup tweets (e.g. `Customer: Just setting up my Twitter. #myfirstTweet`) followed by support links and customer problem descriptions. We implemented turn-aware parsing to isolate the customer's actual complaint turn from setup metadata.
* **7. Margin-based confidence calibration:** Rather than relying on raw softmax probabilities or uncalibrated rule sums, confidence is calculated using intent dominance (margin over runner-up), keyword strength, and historical retrieval agreement across top-3 cases. This reduced the Expected Calibration Error (ECE) to **0.074** (7.4%) and populated the 80%–92% confidence band for clear cases.
* **8. Strict retrieval leakage control (runtime golden exclusion):** We implemented an automated leakage audit (`scripts/leakage_audit.py`) that strictly removes golden set conversation IDs from the TF-IDF search index at runtime, preventing the model from cheating via verbatim historical retrieval.
* **9. Stratified golden set sampling (25 per intent category):** Natural Twitter data is heavily skewed toward routine inquiries. If we evaluated on raw traffic, a model with 0% accuracy on driver assault would still score ~90% overall accuracy. Stratifying 25 examples across all 8 canonical intents (200 total) guarantees rigorous testing on safety and payment risks.
* **10. Dual-baseline comparison:** We established both a trivial baseline (majority class prediction + always escalate) and a simple baseline (1-nearest-neighbor TF-IDF retrieval without safety rules) to prove that the proposed hybrid system provides statistically meaningful gains in macro-F1 and safe automation coverage.
* **11. Deterministic fallback for LLM-as-judge evaluation:** While provider-backed evaluation (Groq / NVIDIA) provides nuanced semantic scoring, rate limits or missing API keys break local reproducibility. We engineered a deterministic 5-dimension rubric fallback (`groundedness`, `correctness`, `completeness`, `tone`, `safety`) so the pipeline can be reproduced entirely offline in under 3 minutes.
* **12. Dedicated `other_or_unclear` intent category:** Forcing vague messages (e.g. "hey check dm", "@Uber_Support help") into concrete problem categories leads to hallucinated answers. Reserving an explicit fallback category allows low-confidence messages to trigger clarifying flows or human triage safely.
* **13. Explicit DataFrame object-casting in Streamlit data editor:** Streamlit's data editor returns Arrow string arrays for edited tables. Assigning empty reviewer notes into typed columns triggers pandas `TypeError: Invalid value for dtype float64`. We cast dataframes to object dtype before assignment to prevent crashing during human evaluation reviews.
